# LifeModel M6 可视化 — 设计稿（v0）

> **一句话定位**：前五个模块管"怎么记、怎么答、怎么管"，M6 管**让记忆的主人看懂**——
> 这份资产里到底有什么、每条哪来的、我删掉的东西是不是真的没了。
> 研究对象是"个人记忆档案的可视化形态"，不是再给实验室添一块看板。

---

## 0. 为什么要单独立一个板块

架构原则里写着：**"资产归本人、由本人控制：看/改/删/限用途/迁出，且改动要生效"**
（docs/LIFEMODEL_ARCHITECTURE.md §0）。现在回看这个承诺，M5 把"改/删/限/迁"的 API
做全了（`correct`/`forget`/`revoke_purpose`/`export`），但"**看**"——也就是一切控制
的前提——没有任何模块负责。用户不可能删一个他没见过的东西，也不可能纠正一条他
不知道记错了的记忆。

行业里已经踩过这个坑，方向很明确：

- **ChatGPT Memory**：早期只在后台默默攒记忆，用户看不见 → 后来被迫加上
  Settings→Manage Memory 列表、memory summary 画像摘要、"Memory updated"
  气泡提示。**透明查看是补出来的需求，不是设计出来的。**
- **Microsoft Recall**：全屏幕时间线被安全界骂成"灾难"，核心火力点就一条——
  **用户不知道自己被记了什么**。反过来说，一个把记了什么摊开的查看器，
  正是这类系统建立信任的唯一手段。

对我们自己也有直接收益：现在排查 LME/LifeStream 判错，做法是人工翻
`results/lme150_rlx1/models/<qid>.json` 的原始快照——M6 就是把这个手艺活
产品化、顺便变成给用户的能力。

**M6 与研究看板（hyra/web.py + research.json）是两类东西**，先划清边界：

| | 研究看板（已有） | M6 可视化（本设计） |
|---|---|---|
| 读者 | 研究者/PI | 记忆的主人（产品用户） |
| 回答的问题 | 研究走到哪了、谁领跑、差距在哪 | 系统记了我什么、哪来的、删干净了没 |
| 数据源 | EB + report.json + research.json | `model.export()` 快照（资产本体） |
| 更新频率 | 每轮实验 | 随资产实时变化 |
| 判断标准 | 分数、通过率 | 普通人能不能看懂、查到、验证 |

两边唯一的共同点是"一处数据、多视图渲染"这条看板原则——M6 的单一事实源
就是 `export()` 快照，禁止旁路读库。

## 1. 数据底座：快照里到底有什么

先把 `export()["asset"]` 的字段逐个翻译成"给用户看什么"。以下例子全部来自
一个跑完整个生命周期的真实快照（LifeStream seed=7，213 条记录、5 次控制事件、
4 条派生，见附录 A）和 lme150 真实对话摄入快照（`28dc39ac.json`）。

### 1.1 `hist` —— 时态流水账本账（核心）

```
hist["source|slot"]            -> [[value, from_day, kind, expires, rid], ...]
hist["claimer|about|slot"]     -> 同上（三段键 = 关于某实体的断言）
```

只追加不涂改。一条边 = 一个取值 + 生效日 + 类型 + 失效日 + 来源记录号。
真实例子（seed=7）：

```
self|city      -> ["深圳", 33, "correction", None, "r0182"]   # 本人纠正
self|device    -> ["手机为主",18,"statement",None,"r0011"]
                  ["电脑为主",39,"update",   None,"r0186"]
                  ["平板",    78,"correction",None, None]      # ← 用户手动纠正，无 rid
self|exercise  -> ["",74,"retraction",None,"r0193"]           # 撤回=墓碑边
表姐|risk      -> 7 条 hearsay 边（激进/中性/保守来回拉锯）
self|妈妈|city  -> 关于"妈妈"的三段键实体断言
```

`kind ∈ statement|update|correction|retraction|suggestion|hearsay|derived|alias`；
`source ∈ self|other|assistant|device|doc|inference|system` + 具名人物（表姐、同事小李）。

**可视化的第一性问题全部在这张表里**：当前的值怎么算（max-from 规则：
取 `from_day<=读日` 的最新边，retraction 即墓碑）、谁是本人说的、谁是传闻、
谁被取代、谁死了。

### 1.2 派生与前提（M3 的账）

```
drv         slot -> {"premises": {前提槽: 前提值}, "value": 派生值}   # 活的派生
drv_log     [{slot,value,supports:[rid],day,id,src,seq}]              # 全部派生事件
pending_drv 前提记录还没到位的候着队列
rsv         rid -> (slot, value)     # 记录号解析表
rday        rid -> 撰写日            # 前提的"时间秩序"检查
```

真实例子：快照里 4 条派生事件，活了 1 条死了 3 条，死因各不相同——

| 派生 | 前提 | 结局 | 死因 |
|---|---|---|---|
| `elder_plan=陪护优先排程` | r0000=`city:深圳` | **死** | day33 本人把 city 纠正成"杭州"，前提值对不上 → 分歧杀 |
| `plan_hint=周末上午安排` | r0190=`family:需照顾老人` | **死** | day55 `forget(family)`，前提槽被整槽删 → 前提没了 |
| `routine_fit=晚间例行可保留` | r0195=`plan_hint`（另一条派生）| **死** | 链式陪葬——前提是派生，派生死了它也死 |
| `habit_fit=记录习惯可持续` | r0197=`creed:每天记录` | **活** | creed 从没变过 |

这组数据是"更新痕迹"视图最好的展示素材：派生不是黑盒，每条都能说出
**凭什么活、因什么死**（drvprov 探针已经把这点做成了可答接口）。

### 1.3 控制面（M5 的账）

```
journal   [{"op":"forget","scope":{...},"slot":s,"removed":n},
           {"op":"correct","slot":s,"value":v},
           {"op":"revoke_purpose","purpose":p},
           {"op":"export"}]          # 操作流水账，随快照导出
revoked   {"制定本周计划"}            # 已撤回用途集合（数据留、视图拒）
```

seed=7 的 journal 实录（顺序即真实顺序）：

```
1. forget(slot=family)      removed=7     # day55 评测器代用户删槽
2. forget(day 52-53)        removed=7     # day62 区间删 → 值回滚
3. forget(about=妈妈)       removed=3     # day74 实体级遗忘
4. correct(device→平板)                    # day78 用户手动纠正
5. revoke_purpose(制定本周计划)             # day84 撤用途
6. export                                # 每次 export 自己也入账
```

### 1.4 身份与辅助表

```
prov     slot -> [本人说过的所有值]    # "这话我说过没有"的判定库
rvid     slot -> 最新本人写入的 rid    # 现值的"出生证"
aliases  别名->正名                   # 阿伟→朋友阿伟、我妈→妈妈（人物页合并键）
exp      slot -> 失效日              # 槽位租约（过期的值读日即死）
wday     slot -> 最新本人写的日       # 乱序摄入的内部书签
now      已见最大日                  # 快照的"今天"
```

### 1.5 已发现的存储缺口（M6 对系统的反向需求）

调研中撞出来的真实缺口，设计视图前必须先列出来：

1. **原话 `text` 没进边**。`ingest.normalize()` 收到 `text`（原话引用，
   LME 摄入侧每条都带 `<=20 词 quote`），但 `store.append()` 的边只有
   `[value, day, kind, expires, rid]`，`rsv` 也只存 `(slot,value)`。
   **"这条记忆的原话是什么"现在答不出来**——溯源视图要求边上带 text
   或 `rsv[rid]` 扩成 `(slot, value, text)`。
2. **journal 条目没有 day**。`control.py` 记的账不带执行日，审计时间线
   排不出"哪天删的"。需要 `journal.append({..., "day": self._day})`。
3. **手动 `correct()` 写的边 rid=None**（见 `self|device` 第 3 条）。
   溯源卡要能区分"记录流里来的"和"用户亲手改的"——这其实是个该展示的
   信息（用户改动是高信任度来源），不只是兼容问题。
4. **`export()` 自己也入账**。lme150 快照 journal 里 5 条全是 `export`
   （渲染层每次 `model.export()` 都记一条）。产品上要把"系统的读取式
   导出"和"用户主动的迁移导出"区分开，否则审计面板会被 export 刷屏。
5. **作用域导出清空 aliases**（契约 15 防泄）——按用途导出给第三方的
   文档里人物页要少一栏"别名"，UI 要正确处理这个空态而不是显示错乱。
6. **遗忘≠封禁，删历史不拒未来**。seed=7 实测：day74 `forget(about=妈妈)`
   抹掉 3 条，day76 新记录 `r0210`（"我说：住在是上海"，about=妈妈）照常
   写入，`self|妈妈|city` 顶点原地复活。语义本身没错（删的是"当时为止的
   账"），但 UI 若把实体页标成"已遗忘"同时又列着 day76 的新事实，用户
   会理解为"删除没生效"。人物页必须区分**遗忘前历史（已抹）**与
   **遗忘后新增**两种状态；要不要支持"抹历史+拒未来"的强语义（封禁名单）
   是 M6 抛给 M5 的一个真问题。
7. **删除只精确到槽，不精确到实体内的其它维度**。`forget_slot('family')`
   删掉 `self|family` 全部 7 条，但非本人顶点的 `doc|family`、
   `表姐|family` 同日份的同名槽仍在（甚至 day62/69/79 的后到新记录也在）。
   "我删掉了 family"这句话在视图里必须翻译成准确口径：
   **删的是"本人域的 family 顶点"，传闻侧的同名词条与此无关**——
   否则删除验证任务会误判。

## 2. 先行案例调研：别人怎么给人看记忆

| 案例 | 它长什么样 | 能抄什么 |
|---|---|---|
| **ChatGPT Memory** | 两层：①memory summary——自动维护的画像文档，标注"2 小时前更新"，可整删；②旧版 saved memories 逐条列表可删。聊天里弹"Memory updated"气泡→点 Manage | 画像文档是"可理解性"首选形态（跟我们 profile 通道 87.5% 最高分互相印证）；删聊天≠删记忆——资产和来源分离，跟我们的边/记录分层一致 |
| **Mem0 Console / Memprobe**(开源检查器） | Memories 列表+类别筛选+全文搜+详情面板（元数据+原始 JSON）+编辑删除；作用域选择器（user/agent/app/run)；**Retrieval Tester**——输入问题看它实际会检索到什么；**Timeline**——单条记忆的变更史；Graph view（付费档）实体图 | 列表+筛选+详情是基线三件套；"干跑检索"是神器——回答"它会拿我的数据干嘛"不靠想象靠实测；单条变更史=我们 supersede 链的原型 |
| **Zep/Graphiti Dashboard** | 时态知识图谱可视化+debug log；每条边四个时间戳（生效/失效/记录/过期），删掉的旧事实标 invalid 但保留在史里 | 双时态正是我们 `hist` 边的工业版；"删除=标失效不抹记录"的展示惯例——**墓碑要可见**，这正是我们 retraction 边还在 hist 里的理由 |
| **Letta ADE / MemGPT** | 记忆分块（human/persona block）直接可编辑，改=写回；MemfsTreeViewer 树形浏览；一键导出"Memory Palace"自包含 HTML 查看器 | 记忆即文档、文档即可编辑的直感；**快照→静态 HTML** 的交付形态被验证过 |
| **Microsoft Recall / Rewind** | 可滚动的全量时间线+全局搜 | 时间线是"我到底被记了啥"的最直觉形态；同时是隐私反弹的前车之鉴——**可见性必须配随时可删**，查看器上就要有删除入口 |
| **MyLifeBits / lifelogging** | 个人终身档案：faceted 分类（按人/主题/类型/时间多维切片）、标注、透视 | 个人数据的核心交互=多维切片，不是单列表 |
| **GDPR 导出查看器**(Meta DYI / Google My Activity / Memento Mori) | 分类勾选导出、按时间段删、用途开关、导出成可读 HTML 站 | "按用途授权/收回"的成熟 UX 原型=我们 `revoke_purpose`+`state(scope)` 的产品形态；导出物本身可读 |
| **RAG 溯源 UI**(Perplexity / NotebookLM / Attribution Gradients) | 行内引用角标、悬停看原文片段、点击跳到原文段落；attribution gradients 逐句拆 claim 对证据 | 每条结论可点出证据链是标配；我们 `rvid`/`rsv` 天生支持"答案→记录"一跳，差的是"记录→原话"（见 §1.5 缺口1） |

**跨案例提炼出的视图类别**（同一个品类在 3+ 家出现才算数）：

1. **画像摘要**——一份人话的"它是怎么理解我的"（ChatGPT summary、MyLifeBits 叙事）
2. **逐条流水+搜索筛选**——基线形态（Mem0、My Activity）
3. **时间线**——按时间铺开（Recall、MyLifeBits）
4. **实体/图谱浏览**——按"关于谁"聚合（Zep、Mem0 graph）
5. **溯源下钻**——每条到证据（RAG 引用、Mem0 详情面板）
6. **控制面板**——删/撤/导出/审计（ChatGPT manage、My Activity、Solid pod）
7. **干跑自检**——"这个用途会看到什么"（Mem0 retrieval tester）

## 3. 视图清单：M6 = 七个视图

每个视图给：回答什么问题、喂什么字段、形态、为什么选这个形态。
**所有视图共用一份 `export()` 快照**；派生标注在任何视图里都带"推论"徽标
（派生事实不是用户说的，必须区分）。

### V1 流水账时间线 —— "系统到底记了什么"

- **形态**：全部 `hist` 边按 `from_day` 排序铺开，一条一行：
  `day42 · 本人 · device → 电脑为主 · [更新]`；传闻/建议/派生带不同色徽标，
  被区间删掉的边灰掉加删除线（**墓碑可见**，学 Zep/Graphiti）。
- **回答**：我这段时间被记了什么？哪天记的？谁说的？
- **选择理由**：hist 本质就是流水账，时间线是它的零失真直读；
  Recall/My Activity 已证明这是用户接受度最高的形态。
- **字段**：`hist` 全边（kind/source/day/value）；`rsv`/`rday` 解析 rid。

### V2 槽位/域浏览 —— "关于 X，系统现在认为是什么"

- **形态**：左列顶点目录（`who·slot` + 边数，即 `vertex_catalog` 形态，
  按域分组：身份/工作/健康/物品/关系/计划），右列点开的槽位变迁链：
  `深圳@d1 → 杭州@d33[纠正] → （现状=杭州）`。活值加粗，取代值灰显，
  `exp` 租约标"将于 dX 失效"，retraction 标墓碑。
- **回答**：系统现在觉得我住哪？这个值换过几次？
- **选择理由**：`(who,slot)` 顶点是 TemporalGraph 的原生分组维度，
  比按值分类忠实；Mem0 的列表+category 已验证。
- **字段**：`hist` 键→目录、`hist` 边→变迁链、`exp`→租约徽标、
  `prov`→"我说过"角标、`drv`→推论徽标（派生的值当活值展示但必带徽标+前提链入口）。

### V3 人物页 —— "我记的关于 Ta 的事 + Ta 自己说过的话"

- **形态**：每个实体一页（`妈妈`、`朋友阿伟`、`aloy`……），两栏：
  ①**关于 Ta**——所有 `claimer|about|slot` 三段键断言（谁说的折叠成徽标）；
  ②**Ta 自己说过**——`claimer=X` 的传闻/陈述顶点。`aliases` 合并名
  （我妈=妈妈=母亲都归一页）；已删实体显示"已于 day74 遗忘"。
- **回答**：我记着妈妈什么事？小李跟我提过什么？
- **选择理由**：列表页比力导图谱信息量高——TemporalGraph 的实体邻居
  是属性槽不是关系边，图谱留作后续可选层（学 Zep 但不迷信图）。
- **字段**：三段键 `hist`、`aliases`/`forms_of`、journal 的 `forget(about)`。

### V4 画像文档 —— "AI 眼里的我长什么样"

- **形态**：`profile.py` 的域分组画像文档（IDENTITY/健康/爱好/物品/关系/
  计划/时间线/偏好八域），**已验证形态**：profile 通道 150 题实测 87.5–89%，
  是答题最强的通道，也是最像 ChatGPT memory summary 的可读形态。
  每条事实尾部带 `(d23·r0186)` 式证据锚，点开跳 V5 溯源卡。
- **回答**：AI 觉得我是什么样的人？哪里记错了？
- **选择理由**：画像是唯一"整体可读"的形态，且每枪都有实弹（锚点可下钻）。
  产品上可以离线生成、定期刷新（带"更新于 day90"水印，学 ChatGPT）。
- **字段**：`live_bundle`/顶点目录 → 渲染层；证据锚 = `rvid`+边 rid。

### V5 来源溯源 —— "这条哪来的、我说过吗"

- **形态**：每条记忆的溯源卡（点击任何地方的记忆项弹出）：
  `记录号 r0182 · day33 · 本人纠正 · 原话"……" · 此前值=深圳`；
  对传闻额外标"表姐说的，非本人"；对派生给前提链
  `habit_fit ← creed:每天记录(r0197)`。
- **回答**：这话是我说的还是听来的？现在的值是哪条定的？
  "系统说我会弹吉他——我说过吗？"→ `prov` 一查便知（本人/非本人）。
- **选择理由**：RAG 引用 UI 已是用户预期；`prov`+`rvid`+`rsv` 让
  每条结论一跳到记录。**依赖 §1.5 缺口 1 修复**（原话入边），
  否则溯源卡只有值没有原话。
- **字段**：边 `rid`→`rsv`/`rday`、`prov`、`drv.premises`+`_drv_log`。

### V6 控制面板 —— "我删的东西真没了吗、我的数据被拿去做什么"

- **形态**三栏：
  ①**操作流水账**——`journal` 渲染成审计时间线：
  `day55 删除槽 family（波及 7 条记录）`、`day62 删 day52-53（7 条，device 回滚）`、
  `day74 遗忘"妈妈"（3 条）`、`day78 纠正 device→平板`、`day84 撤回用途"制定本周计划"`；
  ②**用途域**——每个 purpose 一张卡：绑哪几个槽、当前看到什么值
  （`state(scope)` 干跑预览）、已撤回的标"已拒绝"红色徽标；
  ③**已删除清单**——被 forget 的槽/实体/时间窗 + 级联死掉的派生
  （`drv_log` 里的死因列）。
- **回答**：删除生效了吗？撤回用途之后它还能看吗？谁动过我的资产？
- **选择理由**：这是 M5 API 的镜像——**每个控制操作都必须有可见证据**，
  否则"资产归本人"只是口号。My Activity 的用途开关、Solid 的授权面板
  是成熟参照。删除和撤回是两个不同动作（数据没了 vs 数据还在但视图拒），
  UI 必须分开表达，这正是 revoke_purpose 的语义。
- **字段**：`journal`、`revoked`、`state(scope)` 预览、`drv_log` 死因、
  `hist` 墓碑边。**依赖 §1.5 缺口 2**（journal 带 day）。

### V7 更新痕迹 —— "这条什么时候变的、那个推论为什么没了"

- **形态**：三个子视图合一页：
  ①**supersede 链**——同槽多版本横向链：
  `city: 深圳@d1 ─纠正→ 杭州@d33`；`device: 手机为主@d18 → 电脑为主@d39 → 平板@d78[用户纠正]`；
  ②**派生谱系**——`drv_log` 全表带状态：
  `elder_plan ✗ 死于前提被纠正 / plan_hint ✗ 死于前提被删 / routine_fit ✗ 链式陪葬 / habit_fit ✓ 活`；
  ③**时间回放**——as_of 滑块：拖到 day50 看当时的值（`state_at` 语义已有），
  或两天 diff 出"这段时间什么变了"。
- **回答**：我记得的哪些事是系统推的？为什么这个推论消失了？
- **选择理由**：LifeStream 的 first/order/window/nchange/duration/drvprov
  探针证明这些查询在数据层已可答，M6 只是把它们变成人能看的画面。
- **字段**：`hist` 边序、`drv_log`/`drv`/`pending_drv`、`exp`。

## 4. 交互原语

不按视图按动词列（任何视图里都该能用）：

- **搜**：全文搜 value/slot/实体名（"吉他"→所有提到吉他的边）。
- **筛**：四维切片——时间窗（day 滑杆）、来源（本人/传闻/建议/派生/设备/文档）、
  人物/实体、状态（活/被取代/已删/将失效）。MyLifeBits 的 faceted 分类。
- **钻**：点任意记忆项→V5 溯源卡；点派生→前提链展开；点槽位→V2 变迁。
- **回放**：as_of 时间机器（拖 day 滑块看历史上任一时刻的资产；
  `state_at` 语义已存在）。
- **对比**：两天/两版本 diff——"上周和现在的我差在哪"。
- **干跑**：用途域预览——"这个用途会看到什么"= `state(scope)` 渲染版
  （Mem0 retrieval tester 的思路）。
- **操作入口**：记忆卡上的就地操作——纠正这条/删掉这条/这个用途别再用——
  直连 `correct()`/`forget()`/`revoke_purpose()`，操作完成后审计时间线
  立刻多一行（操作即事件，journal 本来就是可渲染的）。

## 5. 评测：怎么衡量"看得懂"

对不齐 LifeStream 的自动判分——"看得懂"是人的指标。设计成**用户任务化
探针**（沿用 LifeStream 的命名习惯，先出草案再跑）：

| 任务族 | 用户任务 | 判定 | 对应视图 | 陷阱版 |
|---|---|---|---|---|
| T-trace 真伪题 | "系统说我会弹吉他——我说过吗？" | 找到 prov 判定"非本人" | V5+V2 | 传闻冒充本人说的（hearsay 边混在 self 顶点） |
| T-source 来历题 | "这条记忆哪来的？" | 点到溯源卡找到 rid+原话+day | V5 | 用户手动改的边（rid=None，要识别"用户纠正"来源） |
| T-delete 删除验证题 | "我忘掉的 family 还在吗？" | 视图搜不到 + 控制台有 forget 记录 + 级联死的派生无残留 | V6 | 同名不同槽的误报（删了 family 槽但 family 字样的传闻顶点还在——该不该在？要界定） |
| T-purpose 用途题 | "我的数据被拿去做什么了？" | 列出用途域；撤回域显示"已拒"且干跑预览为空 | V6 | 撤回后作用域导出仍吐文档=泄漏（对齐 expdeny 语义） |
| T-edit 纠错闭环 | "画像说我住深圳，错了，改成杭州" | 画像→定位条目→纠正→重渲染后显示杭州、深圳入痕 | V4→操作→V7 | 纠正后旧值必须可见为"被取代"而不是消失 |
| T-diff 变迁题 | "上个月和现在差在哪" | 拖回放/diff 出新增+变更+删除三类 | V7 | 区间删导致的回滚（值变回旧的而不是消失） |

**指标**（对应质量−成本=总分的老规矩）：

- 任务成功率（找没找对/判没判对）——质量侧；
- 到达证据的点击数/耗时——成本侧（类比 probe_bytes：信息触达成本）；
- 误报率——把已删的当活的、把传闻当本人，这类"看错"比"没找到"更糟，
  对应 must_not 的扣分逻辑。

**对照组**：原始快照 JSON dump（现在人肉排查的形态）vs V1–V7 视图。
预期差距在时间线定位和溯源任务上最大；如果画像视图在真伪题上反而
误导（总结丢细节），那也是有效结论——画像该不该带证据锚就有了实测答案。

**自动化可选项**：view_state 断言式探针（"V6 journal 面板应含
op=forget 且 removed=7"）可用无头 DOM 跑——先把人工任务跑通再说。
